# REST API v1

The API is implemented at `/api/v1`. The executable route registry in [`src/lib/api/v1.ts`](../../src/lib/api/v1.ts) is the source for these contracts and generates OpenAPI 3.0.3. The JSON specification is served at `/api/openapi.json`; interactive Swagger UI is served at `/api-docs`.

## Conventions and security

- JSON success responses use `{ "data": ... }`; errors use `{ "error": { "code": "...", "message": "...", "details"?: [{ "path": "...", "code": "..." }] } }`.
- Invalid JSON or request data returns `400 VALIDATION_ERROR`; unsupported methods `405`; absent resources `404`; state conflicts `409`; rate limits `429`; unexpected errors `500`. Other route-specific responses are listed below.
- Request bodies are strict Zod objects: unknown fields are rejected. Email values are trimmed, normalized to lowercase, and limited to 254 characters. Passwords are 12-128 characters with uppercase, lowercase, a number, and a symbol.
- Mutating same-origin requests must pass the Origin/CSRF check. Authentication and verification cookies are HttpOnly and SameSite; cookies are Secure in production. Access sessions use a rotating refresh cookie with a bounded lifetime; refresh tokens are never returned in JSON or browser storage. `Secure` is also used for HTTPS development cookies.
- Session-authenticated routes use the `marketplace_session` cookie in development or `__Host-marketplace_session` in production. Public registration issues a short-lived `marketplace_pending_email_verification` or production `__Host-marketplace_pending_email_verification` cookie. Verification and resend are bound to that signed cookie; the client cannot choose an email or account ID.
- Public authentication and onboarding-submit routes apply endpoint rate limits. reCAPTCHA v3 is required where noted; server-side verification checks the configured action, hostname, score, and provider result.
- Amazon Login with Amazon is available only for `CUSTOMER` and `VENDOR`. OAuth state, browser binding, nonce, PKCE, and callback/redirect URI validation remain in force. The callback preserves the account type chosen at start. No administrator Amazon login or public admin registration exists.
- Amazon profile fields used are `user_id`, `email`, and `name`. A successful Amazon identity callback marks the Amazon-authenticated account email as verified; local email/password accounts still require Somsuuq verification. Existing local accounts are not automatically linked by matching email.

## Authentication

| Method and path | Access | Request | Success |
|---|---|---|---|
| `POST /api/v1/auth/customer/register` | Public; reCAPTCHA action `customer_register`; rate limited | JSON `{ email, password, recaptchaToken }` | `201 { data: { user } }`; creates CUSTOMER and sets pending-verification cookie |
| `POST /api/v1/auth/vendor/register` | Public; reCAPTCHA action `vendor_register`; rate limited | JSON `{ email, password, recaptchaToken }` | `201 { data: { user } }`; creates VENDOR and sets pending-verification cookie; does not approve vendor |
| `POST /api/v1/auth/login` | Public; reCAPTCHA action `${accountType.toLowerCase()}_login`; rate limited | JSON `{ email, password, accountType: "CUSTOMER" \| "VENDOR", recaptchaToken }` | `200 { data: { user } }`; sets access and rotating refresh cookies |
| `POST /api/v1/auth/logout` | Authenticated customer, vendor, or admin | No body | `200 { data: { loggedOut: true } }`; revokes server session and clears cookie |
| `GET /api/v1/auth/me` | Authenticated customer or vendor | No body | `200 { data: { user, vendorStatus?, vendorVerificationStatus? } }`; returns no tokens or credential material |
| `POST /api/v1/auth/email/verify` | Public; pending-verification cookie; rate limited | JSON `{ code }`, six-digit string | `200 { data: { verified: true, user: { id, accountType } } }`; consumes OTP, verifies the bound account, clears pending cookie, and sets session cookie |
| `POST /api/v1/auth/email/resend` | Public; pending-verification cookie; reCAPTCHA action `email_resend`; rate limited | JSON `{ recaptchaToken }` | `202 { data: { accepted: true } }`; sends only to the registered address bound to the cookie |
| `POST /api/v1/auth/password/forgot` | Public; account-neutral response; reCAPTCHA action `password_forgot`; rate limited | JSON `{ email, accountType: "CUSTOMER" \| "VENDOR", recaptchaToken }` | `202 { data: { accepted: true } }` regardless of whether a matching local account exists |
| `POST /api/v1/auth/password/reset` | Public; rate limited | JSON `{ email, accountType, code, newPassword }` | `200 { data: { reset: true } }`; revokes existing sessions |
| `POST /api/v1/auth/amazon` | Public; CUSTOMER/VENDOR only; reCAPTCHA action selected from account type; rate limited | JSON or form-urlencoded `{ accountType: "CUSTOMER" \| "VENDOR", locale?: "en" \| "so", recaptchaToken }` | `302` redirect to Amazon; sets short-lived browser-bound OAuth state |
| `GET /api/v1/auth/amazon/callback` | Public provider callback | Provider query: `code` and `state`, or `error` and `state` | `303` redirect to selected customer/vendor destination; session cookie set only after successful authentication |

`user` responses contain `{ id, email, accountType, emailVerified }`. A verification code is a six-digit string. Resend's `202` means the backend accepted and completed the mail-send operation; it is not evidence that the recipient's mail provider delivered or displayed the message.

## Administrator authentication and MFA

There is no public administrator registration. Administrator accounts are privately provisioned. Email OTP is required before the MFA challenge. The email/MFA challenge identifier is short-lived, is not an access token, and cannot be used as a marketplace session.

| Method and path | Access | Request | Success |
|---|---|---|---|
| `POST /api/v1/admin/auth/login` | Public; reCAPTCHA action `admin_login`; rate limited | JSON `{ email, password, recaptchaToken }` | `202 { data: { accepted: true } }`; begins admin credential and email-OTP flow |
| `POST /api/v1/admin/auth/email/verify` | Public; rate limited | JSON `{ email, code }` | `200 { data: { challengeId, mfaRequired } }` |
| `POST /api/v1/admin/auth/mfa/verify` | Valid email-OTP challenge; rate limited | JSON `{ challengeId, code }`; code is six-digit TOTP or formatted recovery code | `200 { data: { user } }`; sets admin session cookie |
| `POST /api/v1/admin/auth/mfa/setup` | Valid email-OTP challenge with MFA disabled; rate limited | JSON `{ challengeId, secret }`; Base32 `A-Z2-7`, 32-64 characters | `200 { data: { setup: true } }`; stores encrypted secret; secret is not returned |
| `POST /api/v1/admin/auth/mfa/enable` | Valid email-OTP challenge; rate limited | JSON `{ challengeId, code }`; six-digit TOTP | `200 { data: { user, recoveryCodes } }`; enables MFA, sets session, returns recovery codes once |
| `POST /api/v1/admin/auth/logout` | Authenticated ADMIN | No body | `200 { data: { loggedOut: true } }`; revokes session and clears cookie |

## Vendor onboarding and review

The application fields below are optional when creating a draft so a vendor may complete onboarding incrementally. PATCH requires at least one field. Status, verification status, reviewer, and review decision fields are server-managed and are not accepted as vendor input.

| Method and path | Access | Request | Success |
|---|---|---|---|
| `GET /api/v1/vendor/onboarding` | Authenticated VENDOR; verified email or recognized Amazon identity | No body | `200 { data: { application: Application \| null } }` |
| `POST /api/v1/vendor/onboarding` | Authenticated VENDOR; verified email or recognized Amazon identity | JSON subset of application fields | `201 { data: { application } }`; creates DRAFT |
| `PATCH /api/v1/vendor/onboarding` | Authenticated VENDOR; verified email or recognized Amazon identity | JSON non-empty subset of application fields | `200 { data: { application } }`; updates own DRAFT or CHANGES_REQUESTED application |
| `POST /api/v1/vendor/onboarding/submit` | Authenticated VENDOR; verified email or recognized Amazon identity; reCAPTCHA action `vendor_onboarding_submit`; rate limited | JSON `{ recaptchaToken }` | `200 { data: { application } }`; moves eligible application to PENDING |
| `GET /api/v1/vendor/onboarding/status` | Authenticated VENDOR; verified email or recognized Amazon identity | No body | `200 { data: { status, verificationStatus, submittedAt, reviewedAt, rejectionReason?, informationRequest? } }` |
| `GET /api/v1/admin/vendors/applications` | Authenticated ADMIN | Query: `status?`, `search?`, `cursor?` (UUID), `limit?` (1-50, default 20) | `200 { data: { applications: Application[], nextCursor: UUID \| null } }`; drafts excluded; search covers business/store/contact names and email |
| `GET /api/v1/admin/vendors/applications/{applicationId}` | Authenticated ADMIN | UUID path parameter | `200 { data: { application } }` |
| `POST /api/v1/admin/vendors/applications/{applicationId}/approve` | Authenticated ADMIN | JSON `{ note? }` (max 1000 characters) | `200 { data: { application } }`; creates audit record |
| `POST /api/v1/admin/vendors/applications/{applicationId}/reject` | Authenticated ADMIN | JSON `{ reason }` (3-1000 characters) | `200 { data: { application } }`; creates audit record |
| `POST /api/v1/admin/vendors/applications/{applicationId}/request-information` | Authenticated ADMIN | JSON `{ message }` (3-1000 characters) | `200 { data: { application } }`; moves the application to CHANGES_REQUESTED and creates an audit record |
| `POST /api/v1/admin/vendors/applications/{applicationId}/email-retry` | Authenticated ADMIN | JSON `{ event }` | `200 { data: { application } }`; retries an unsent failed notification |
| `POST /api/v1/admin/vendors/{vendorId}/suspend` | Authenticated ADMIN | JSON `{ reason }` (3-1000 characters); `vendorId` is the vendor user UUID | `200 { data: { application } }`; suspends an approved vendor and creates audit record |

Application fields are `businessName` (2-200), `storeName` (2-120), `businessType` (2-100), `description` (max 2000), `contactName` (2-160), normalized international `phone`, `country`, `region`, `city`, optional `district`, `address` (max 300), and `marketAssociation` (max 200). They are optional on create and patch. Country, region, city, and district values are checked against the supported local location dataset, with explicit manual `Other` values for locations not covered. The response includes application ID, statuses, those fields as nullable values, submission/review timestamps, rejection/information-request text, and created/updated timestamps. Admin application records also include the vendor's `{ id, email }`.

Admin review is currently accepted only from `PENDING` or `UNDER_REVIEW`. Invalid transitions and concurrent state changes return `409`. Vendors cannot set their status, and selling access is restricted to approved vendors.

The initial page request is checked by `src/proxy.ts`. If the access JWT has expired, the server validates and rotates the refresh cookie, forwards the replacement cookie to the page request, and keeps the normal database-backed route guards authoritative. A failed database/provider connection is logged as a temporary restoration failure and is not treated as proof that the user logged out.

Vendor application notifications are recorded only after the application status transaction succeeds. Each event stores the registered account email, SMTP-acceptance timestamp, attempt count, last attempt, and sanitized failure text. SMTP acceptance is shown as accepted, not delivery-confirmed; failed records can be retried from the admin application detail page.

Catalog text search covers product names and descriptions in both languages, brand, category and parent-category names, and vendor/store names. Rating aggregates exclude hidden reviews. Completed-purchase counts are distinct marketplace orders with successful payment and delivered vendor orders; refunded lines are excluded. Search, filters, and catalog data are backed by the database rather than static product listings.

Review uniqueness is enforced by the unique order-line relation in PostgreSQL as well as by eligibility checks in the review transaction. Return quantities reserve only the requested units; refunds are simulated only after the vendor confirms receipt, and cumulative refunds cannot exceed the captured payment. Vendor and customer access is scoped to their own sub-orders and requests.

Mobile-money checkout is simulation-only. Test numbers ending in `0000` deterministically fail; other valid numbers deterministically succeed. This convention tests the mock adapter and does not describe real provider behavior. Payment attempts, receipts, and SMS outbox entries are explicitly marked simulated. SMS messages are saved to the database outbox only; no SMS provider is called and there is no send operation.

Reservation responses contain server-generated `expiresAt` and `serverNow` timestamps. The browser countdown is display-only; payment revalidates the reservation and expiry in the database transaction. A scheduled Vercel Cron job invokes `/api/cron/marketplace` every minute; set `CRON_SECRET` in production so only authenticated cron requests can trigger expiration cleanup.

Customer, vendor, and administrator views use authenticated polling while visible, with App Router refresh for server-rendered dashboards. Polling pauses in hidden tabs and refreshes on focus or reconnection; browser refresh is not required.

Customer order placement and vendor order status changes create customer notifications. The customer header shows unread counts and refreshes them periodically; customers can mark one or all notifications read. Product options are stored on variants; products without options use a single standard stock/pricing variant, while category suggestions are derived from existing category/subcategory names and slugs.

## Common errors

| Status | Typical code | Meaning |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Invalid JSON, body, query, or path parameter; details identify safe field paths/codes |
| `401` | `UNAUTHENTICATED`, `EMAIL_VERIFICATION_SESSION_REQUIRED` | Missing/invalid session or pending-verification cookie |
| `403` | `FORBIDDEN`, `EMAIL_NOT_VERIFIED` | Authorization, same-origin/CSRF, email-verification, or reCAPTCHA rejection |
| `404` | `NOT_FOUND`, `APPLICATION_NOT_FOUND` | Route or resource does not exist |
| `405` | `METHOD_NOT_ALLOWED` | Unsupported method |
| `409` | `CONFLICT`, `INVALID_APPLICATION_TRANSITION` | State conflict or invalid lifecycle transition |
| `413` | `PAYLOAD_TOO_LARGE` | Amazon form body exceeds its request limit |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | Amazon start request is not JSON or form-urlencoded |
| `429` | `RATE_LIMITED` | Endpoint rate limit reached |
| `500` | `INTERNAL_SERVER_ERROR` | Unexpected server failure; internal details are not exposed |
| `503` | `SERVICE_UNAVAILABLE` | Required external integration is unavailable |

The exact code and safe message can vary by specific domain error. Errors do not expose credentials, tokens, OTP values, provider secrets, or internal exception details.

## Not implemented

Coupon, payout, market-management, and video-call APIs are not implemented. Proposed routes for those features are intentionally not listed here.
